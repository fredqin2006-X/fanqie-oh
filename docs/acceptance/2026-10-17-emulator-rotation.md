# 2026-10-17 模拟器横屏与画面黑缝复测

用户反馈上一包“强制横屏”仍无效，要求先在模拟器完成排查，不先交付安装包。随后指出画面偏下、侧边有黑缝。本轮只构建和安装 x86_64 调试验证包，未交付新的 ARM64 包，未操作已连接的手机，未推送或发布。

## 已复现的原因

1. 固定引擎的 `PlatformChannel.ets` 在 `SystemChrome.setEnabledSystemUIMode` 成功分支没有调用 `result.success`。播放器先进入全屏、后获得尺寸时，隐藏系统栏的 Future 一直未完成；后续方向、返回和手动横屏排在同一队列中，因此原生方向仍为 0，窗口保持 1256×2760。Widget 测试此前用立即完成的 mock，未覆盖这种缺失回传。
2. 改用有成功回传的手动 overlays 接口后，原生窗口成功横屏到 2760×1256；但原生开孔已是左 108、上 0，Flutter 仍报告旧竖屏顶部边距。合并最大值造成额外 108 像素顶部空白，画面中心向下偏移 54 像素，物理竖置模拟器中表现为一侧黑缝。

## 修复

- 鸿蒙播放器系统栏走 `SystemUiMode.manual`，方向仍显式设置主窗口的固定横/竖策略；避免等待不回传的 mode 接口。其他平台保留原策略。
- 原生同时获取开孔、当前可见系统栏与导航指示区，附带当前窗口宽高。收到与 Flutter 视图尺寸一致的原生结果后，以它为安全区依据，消费旧 Flutter padding，清除旧 cutout feature 的重复影响；原生数据不可用时才使用 Flutter 兜底。真实开孔侧仍保留空白，不裁切视频去填开孔。

## Pura 90 Pro 运行证据

环境为 HarmonyOS 7 / API 26、x86_64。冷启动安装后，从实际短剧入口点击进入；未通过旋转模拟器按钮来替代应用请求，也未使用热重载作为验收。

| 检查 | 实际结果 |
| --- | --- |
| 进入全屏 | 原生窗口及屏幕截图从 1256×2760 变为 2760×1256；SDK preferred orientation 为 2 |
| 点击“强制横屏” | 真正横屏，Flutter fullscreen=true、forceLandscape=true；方向队列 Future 完成 |
| 连播与反复进出 | 更换播放器后仍横屏；系统 Back 恢复竖屏和常规控件；再次点击手动横屏正常 |
| 实际播放 | firstFrame=true、playing=true，位置持续推进且截图画面变化，无播放错误 |
| 修复前画面边界 | 截图中非黑内容约为 `(434,108)–(2434,1256)`，顶部额外空白 108 像素 |
| 修复后画面边界 | 截图中非黑内容约为 `(340,0)–(2528,1256)`，覆盖完整高度，垂直中心为 628 |
| 原生安全区 | 横屏左 108、上/右/下 0；返回常规竖屏后上 136、下 98、左/右 0 |

截图、逐次窗口 dump、脱敏字段 VM 检查和像素边界统计在忽略目录 `local-reports/rotation-20261017/`，不把视频画面、原始日志、认证 VM 地址或设备数据提交到 Git。最终截图为 `gap-final.jpeg`。源画面等比完整显示，长边剩余空间仍按片源比例保留，当前可用区域内居中。

构建链路：`517f89` 复现包、`d51ad4` 原生追踪包、`dafaf0` 方向队列修复包、`6911e2` 旋转安全区修复包。每次构建各自保留本地提交和输入清单。最终相关回归结果以该修复构建记录为准。

## 验证边界

这是 API 26 模拟器运行结果，不是 API 23 ARM64 真机验收。通过的是系统 Back 返回事件；本轮注入的边缘滑动没有触发模拟器系统返回，不能把它记为物理返回手势通过。当前仅供用户查看模拟器效果，后续 ARM64 安装包需另行构建。
